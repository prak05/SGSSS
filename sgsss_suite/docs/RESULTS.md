# Measured results on the held-out test set

Generated by `scripts/evaluate.py` (automatic per-project seed, 260 instances, 276s). Raw per-instance numbers: `docs/results.csv`.

Setup: all six solvers get the same budget of schedule evaluations (SSGS decodes): set automatically from each project: 10 x activities x (1 + resource pressure, capped at 2), e.g. 400-2800 here. Every decode is counted, including both passes of justification. None of these instances was used for training (training used `data/train`, a different set of PSPLIB parameter groups and RG30 files).

Winner rule (applied identically to every algorithm): makespan → total finish time → resource levelling → reliability (mean evaluations over 5 seeds, only for algorithms still tied) → runtime.

## Summary

- A proposed method (TS or PSS) won **232/260** instances (89.2%).
- Of those wins, 75 were decided by strictly shorter makespan; the rest were makespan ties decided by: reliability (mean evaluations over 5 seeds) 33, total finish time 70, resource levelling 5, runtime 49.
- A baseline found a strictly shorter makespan than both TS and PSS on **15** instances: j3011_5.sm, j305_2.sm, j305_3.sm, j305_5.sm, j309_2.sm, j601_5.sm, Pat15.rcp, Pat17.rcp, Pat24.rcp, Pat37.rcp, Pat43.rcp, Pat44.rcp, Pat5.rcp, Pat53.rcp, Pat60.rcp.
- Feasibility audit (independent precedence + capacity check): **260/260** instances fully feasible for all six solvers.

*Optimum = proven optimal makespan (J30, from PSPLIB); best known = best published upper bound (J60/J90/J120, from PSPLIB). The lower bound is max(critical path, resource work bound).
